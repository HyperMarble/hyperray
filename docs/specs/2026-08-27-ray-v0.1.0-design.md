# ray v0.1.0 — Design (revised 2026-08-27)

Supersedes `2026-08-25-ray-v0.1.0-design.md`. Every correction below was
found by running the thing, not by reasoning about it. Where a claim has
not been verified by execution, it says so.

## What this is

`ray` verifies **one fixed coding task or one fixed PR against a specific
issue** — never open-ended software behavior.

The task fixes the verification problem: a fixed instruction, base commit,
solution diff, changed scope, environment, and observable requirements. That makes
the **requirement set** closed; it does not automatically make every
concrete input domain finite. For example, one declared category `x >= 0`
contains many distinct inputs, and an implementation may behave correctly
at `x = 0` but incorrectly at `x = 1`.

Ray therefore accepts a proof universe only when each input region is one
of:

- a singleton concrete input tuple;
- a finite typed set expanded into one distinct proof point per tuple; or
- a compiler-derived symbolic region handled by a universally quantified
  proof.

A finite list of semantic category names is not itself a finite input
universe. Sampling witnesses never closes a category. If Ray cannot build
one of the three representations above, the result is `PROOF BLOCKED`.

### Two proof obligations, both required

**A. Implementation correctness** — no bounded execution of the actual
solution falsifies the compiled formal property.

**B. Grader soundness** — no behavior that falsifies the compiled formal
property passes the task's verifier.

Neither replaces the other. An earlier revision of this document retired
obligation A and aimed `ray` solely at test adequacy; that is wrong.
Detecting false positives is necessary and was the thing missing, but
`ray` must also verify that the code logic satisfies the frozen formal
property model.

### spec.md is proof-language source

`spec.md` is authored manually via the `spec` skill, from the
instruction, the base code, the solution patch, every relevant branch and
outcome, and the fixed environment. Tests are read **only as evidence of
what is currently graded** — never as a source of requirements.

`spec.md` is neither a PRD nor an instruction that solver code reads or
"follows". It is the strict machine-readable source language for finite
domains, assumptions, and formal properties. `speccompiler` parses and
validates that source once and emits canonical typed formal-property IR.
Every proof stage consumes that IR; no proof stage interprets Markdown or
prose. The certificate binds both the frozen source digest and the compiled
property digest and rejects a missing, incomplete, detached, or stale pair.

If the authored property expresses the wrong intent, that is an upstream
authoring error outside the guarantee of that run. Structural validation can
prove type correctness, finite closure, totality, disjointness, and provenance;
it cannot prove what a human intended. Phase-A review records that meaning
decision separately from the mathematical proof.

The direction never reverses:

```
instruction + base code + solution/PR
            ↓  spec skill / manual judgement
        frozen spec.md source
            ↓
       strict speccompiler
            ↓
 canonical formal-property IR
            ↓
verify code and verifier predicates
```

### The guarantee

Relative to the accepted compiled property model:

> The reference implementation satisfies the formal property, and no behavior
> that falsifies that property is accepted by the verifier.

## Two roles, and ray belongs to one

- **Author** (human or AI) writes the task, writes `spec.md`, runs `ray`,
  fixes what it reports. Sees everything.
- **Solver agent** receives `instruction.md` only. Never sees `spec.md`,
  never sees `ray`, never sees the tests.

`ray` runs entirely on the author's side and is finished before a solver
starts. "GOOD TO GO" is therefore a claim about the *task* — it is sealed
such that no solver can pass without meeting the requirements — not a
claim about any particular solution.

```
  write task  →  ray check  →  (if sound) load into Harbor/Inspect  →  solver agents run
```

## The formal property and verifier predicate

The compiled formal-property IR defines the required behavior predicate.
The independently translated verifier defines the acceptance predicate. Ray
proves their relationship rather than comparing Markdown text:

| direction | failure | consequence |
|---|---|---|
| row has no test | requirement unenforced | solver skips it and passes — **false positive** |
| row not stated in instruction.md | requirement unstated | solver cannot know — **unfair fail** |

The proof engine never parses `instruction.md`. Instruction-to-property
meaning is Phase-A author/reviewer evidence, not an NLP theorem.

**Do not derive spec.md's rows from the tests.** Rows come from intent
plus the reference solution's real branches. A spec written while reading
the tests contains whatever the tests contain, so comparing them
afterward can never find a missing test — the ruler was cut to fit. This
happened during authoring and produced a clean-looking result that could
not, by construction, have found anything.

## Task bundle format

The 2026-08-25 draft assumed source files on disk. Most real tasks are
not shaped that way. Measured across 113 deep-swe tasks:

```
task/
  instruction.md          # prose, 5-85 lines
  spec.md                 # formal-property source (authored locally, never shipped)
  task.toml               # repo, base_commit_hash, docker_image, timeouts
  environment/Dockerfile
  tests/test.patch        # the tests ADDED for this task, 400-1700 lines
  tests/test.sh           # the verifier
  solution/solution.patch # the reference fix, against base_commit
```

Consequences that the earlier draft missed:

- **There is no source on disk.** The solution is a patch against a base
  commit. Anything that edits solution source needs the repo checked out
  and the patch applied — which for a real task means the task's Docker
  image, because the repo needs its own toolchain to run at all (numba's
  is 4.6GB).
- **`ray` must never manage containers.** It takes a command string. The
  author already has the environment running; `ray` attaches to it.
- **Exit status is not the pass signal.** Harbor-style `test.sh` ends in
  `exit 0` unconditionally and writes the verdict to
  `/logs/verifier/reward.txt`. Trusting the exit code marks everything
  "covered" against that bench, forever, silently. The pass signal must
  be task-declared.

## Layer status, as measured

| layer | obligation | designed to | actually does |
|---|---|---|---|
| 1 `spec-lint` | — | completeness, disjointness, undeclared values on the frozen spec | does exactly that |
| 2 `coverage` | **B** | expand every combination **and flag those with zero enforcing test** | built 2026-08-27 — declarative half |
| 2 `enforce` | **B** | break each obligation, confirm the *declared* test is what fails | built 2026-08-27 — executable half; found 5 proven false positives on the cron fixture |
| 2 `conform` | **A** | check the real solution against every expanded requirement | built 2026-08-27 — exhaustive over the fixed scope; gates on witness relevance |
| 3 `oracle` | **A** | prove a reference model against the compiled formal property | works, not yet driven from canonical property IR |
| 4 `diff-test` | **A** | compare the real implementation against the proven model | works |
| 5 `dep-harvest` | A | real edge values from a pinned dep's own suite | works — an input, not a gate |
| — `sufficiency` | A | solution behaviour outside the compiled property model | legacy wording was backwards; the finding is about disagreement among artifacts, not malformed Markdown |
| — `mutation` | neither | flip operators/constants, run tests | **must not gate** — see below |

### Layer 2 is the missing core

The original design already specified the check this whole tool exists
for — *"cross-references the generated combination matrix against the
actual test file: flags any required combination with zero matching
test."* It was never implemented, and it has never run: `/f:json` (see
below) made the layer fail on every task, and a failing layer renders as
"skipped," which reads like a missing binary rather than a bug.

### Mutation is actively harmful and should not gate

On the cron task, `mutation` printed *"75 mutant(s), all caught by the
tests"* — on a task where deleting any of five whole guards leaves all 16
tests passing. It measures the wrong thing carefully: operator and
constant flips are small edits, while a solver omits a requirement
entirely. A pass that reports GOOD TO GO when the answer is NOT READY is
worse than no pass, because it is ray committing the exact failure ray
exists to prevent. Demote to advisory or remove.

## Verified limits found by running

- **PICT has no JSON output.** The earlier draft specified `/f:json`.
  pict 3.7.4 rejects it — `Unknown option: /f:json`, exit 3. Real output
  is tab-separated with a header row. Fixed 2026-08-27.
- **Deleting a guard and watching the tests is sound in one direction
  only.** No test failing after a confirmed violation proves the
  requirement is unenforced. A test *failing* does not prove the
  requirement is enforced — the edit may have broken something else. Only
  GAP and UNKNOWN are defensible verdicts; "covered" is an assumption.
- **Equivalence cannot be established by sampling.** Concluding "this
  edit changes nothing" from a finite set of inputs produced 9 wrong
  verdicts out of 11 when the inputs came from the task's own tests. The
  finding direction needs one witness; the all-clear direction needs a
  proof.
- **Token matching is not requirement matching.** Comparing
  `instruction.md` against `test.patch` by shared identifiers flagged 95%
  of 113 tasks, with "requirements" like `bool`, `json`, `data`. Whether
  a test enforces a requirement is a question about meaning; three
  attempts at a textual proxy all failed the same way.
- **The semantic step is unavoidable and appears twice** — writing
  `spec.md`, and pairing each row with the test that enforces it. Both
  are per-task authoring work. Everything downstream of that pairing is
  exact.

## Finite adapter task profile

Ray verifies behavior at a small, frozen boundary. It does not require the
task author to rewrite ordinary implementation code or Ray to reconstruct
every internal loop, class, container, and call path.

Each accepted task provides:

1. A strict `spec.md` source that compiles to the complete finite concrete
   input universe, operation/reset policy, assumptions, formal properties, and
   finite observable outcomes/effects.
2. A frozen adapter that invokes the real changed operation through canonical
   typed requests and returns canonical raw traces.
3. A verifier that can access the solution only through that adapter boundary.
4. A hermetic supervisor that gives the implementation only the declared
   operation and inputs, in a fresh process, with no test identity, ambient
   environment, clock, randomness, or undeclared cross-call state.

The actual Python, Rust, or C++ implementation may contain ordinary OOP,
loops, branches, and calls. Those internals are opaque to the global grader
proof. Ray executes the real adapter over every declared input to check the
reference. It then substitutes every complete behavior table at the same
boundary and runs the frozen verifier to construct the exact `TestsPass`
truth table. Consequently a missing test is exposed directly: two tables that
differ only at the missing point receive the same passing verdict.

For a conforming Ray-authored task, Ray also generates the authoritative
hidden verifier directly from canonical formal-property IR and the complete adapter
point universe. That verifier checks every point, so its accepted behavior set
equals Spec by construction. Handwritten project tests may still run as
additional checks, but they do not grade the solver unless Ray separately
proves they reject no Spec-compliant behavior. This removes both missing-test
false positives and accidental extra-test unfairness from the primary grader.

This is language-independent without being semantics-free. Soundness depends
on proving boundary closure: the verifier has no other solution channel, the
implementation has no test-context channel, reset/determinism hold, all
requests and responses are transcripted, and undeclared behavior maps to the
canonical `Other` outcome. Failure of any closure condition is `PROOF
BLOCKED`.

Compiler IR remains useful for checking that the adapter binds the intended
changed symbol and for accelerating large finite products. It is not required
to encode internal control flow when executable boundary enumeration is
complete. Static Test IR/SMT/BDD may accelerate the truth-table construction,
but must match the executable adapter semantics.

## THE TARGET PIPELINE

This is the design being built. It is **not** a claim about what the
repository implements. Each phase carries its real status, and the honest
gap between the two is the point of writing it down.

```
Fixed task or PR
        ↓
Freeze artifacts and environment
        ↓
Extract instruction, code, tests, environment INDEPENDENTLY
        ↓
Author and validate machine-readable spec.md
        ↓
Freeze spec source
        ↓
Compile spec into canonical formal-property IR
        ↓
Compile code, tests, and environment into Ray Semantic IR
        ↓
Prove reference code satisfies spec
        ↓
Prove passing tests implies satisfying spec
        ↓
Prove tests do not require behaviour outside spec
        ↓
Execute generated counterexamples
        ↓
Produce verification certificate
```

| phase | what it does | status |
|---|---|---|
| 1 Freeze the task | hash every artifact; three workspaces (base+old tests, base+new tests, base+solution+new tests) to prove the tests expose the issue and the reference passes | **not built** — no hashing, no workspace triple |
| 2 Bounded behaviour | changed functions, branches, boundaries, exceptions, effects, callers, and what must stay unchanged | **partial** — patch line-scoping only; no call paths or effects |
| 3 Four independent models | Instruction IR, Code Change IR, Test IR, Environment IR, kept separate | **partial** — spec parsed, code outcomes extracted shallowly; no Test IR, no Environment IR |
| 4 Candidate requirements with provenance | every behaviour tagged with its evidence; disagreements are findings, never majority vote | **not built** |
| 5 Semantic parameters | complete, disjoint, **reachable**, relevant | **partial** — spec-lint proves complete + disjoint on declared values; reachability is not checked |
| 6 Constraints | impossible combinations declared, not sampled away | **not built** |
| 7 Requirement rows | id, conditions, operation, required outcome, **forbidden outcomes**, effects, preserved behaviour, instruction source | **partial** — rows carry conditions + required outcome + enforcing test; no forbidden outcomes, no ids, no provenance |
| 8 Validate and freeze | validate the proof-language source; bind its hash and compiled property hash | **partial** — spec-lint validates source structure; full derivation binding is pending |
| 9 Ray Semantic IR | one vocabulary for all artifacts | **not built** — this is the keystone everything below depends on |
| 10 Prove the reference | `Scope ∧ CodeBehaviour ∧ ¬Property` | **not wired** — oracle/Verus/ESBMC exist, none driven from canonical property IR |
| 11 Test oracles | what each test actually observes and accepts | **not built** — only test names |
| 12 Global false-positive proof | `BehaviourModel ∧ TestsPass ∧ ¬Property` | **approximated** — `enforce` samples adversaries instead of proving over the outcome space |
| 13 Fairness proof | `BehaviourModel ∧ Property ∧ ¬TestsPass` | **approximated** — `intent` matches quoted requirements against instruction.md |
| 14 Execute counterexamples | apply a violating patch, build, run the real verifier, restore | **built** — this is what `enforce` already does |
| 15 Certificate | hashes, mappings, proofs, solver and frontend versions, exact commands | **not built** |

### What VERIFIED requires

Never claimed unless all of: the task is fixed and bounded; the
environment reproducible; the spec complete and non-contradictory;
instruction and spec agree; changed behaviour and spec agree; the
reference satisfies every row; no spec-violating behaviour passes the
tests; no spec-compliant behaviour is rejected; every construct was
translated; every finding was confirmed by execution.

Anything else is `NOT VERIFIED` with a witness, or `PROOF BLOCKED` with
the reason. **A blocked translation must never render as PASS or SKIPPED.**

### The gap, stated plainly

ray today does phases 14 and parts of 2, 3, 5, 7, 8, 12 and 13. It does
not have the IR, the certificate, the freeze, or any real solver proof.
What it has is the execution layer — which the target treats as the
*final confirmation step*, not the product.

The distance is phase 9. Every proof phase depends on one vocabulary, and
without it `enforce` samples where it should prove: a killed adversary
shows one adversary was caught, while `BehaviourModel ∧ TestsPass ∧ ¬Spec`
covers every forbidden outcome the spec names. That is the difference
between "nothing I tried got through" and "nothing can".

## RETIRED WITNESS-FINDING MECHANISM — NON-GATING

The mutation/probe mechanism below predates the Target Pipeline. It is
retained only as historical evidence and as an optional way to find and
execute counterexamples. It cannot establish implementation correctness,
grader soundness, fairness, translation completeness, or `VERIFIED`.
Nothing in this section overrides the Semantic IR and global-proof rules
above.

One mechanism. Not a rule per case. If a future change adds a special case
per kind of requirement, that is the drift this section exists to stop.

```
generate   candidate wrong solutions, mechanically, from a fixed operator
           table over the code the task changed
filter     keep the candidates that behave differently from the real
           solution -- the reference solution IS the oracle for correct,
           so any behavioural difference is a deviation from correct
judge      run the task's own verifier on a deviating candidate;
           it passes  -> a wrong solution passes -> FALSE POSITIVE
```

Only the finding direction is ever claimed. "Differs on an input we tried"
proves deviation. "Agreed on the inputs we tried" proves nothing and is
reported unknown. Concluding equivalence from finite sampling produced 9
wrong verdicts in one sitting; it is undecidable in general and unnecessary
here.

Bounded because the task is fixed: finite mutation points in a finite
patch, a fixed operator table, finitely many probes.

**Verified:** 9 proven false positives on the cron fixture with zero
authored violations and no per-case rules (`internal/enforce/discover.go`,
`tests/discover_test.go`).

### The open piece: where probes come from

A probe is an input both the candidate and the real solution are run on.
Probe selection is the whole difficulty, and it is a source-of-inputs
problem, not another rule.

Measured: four probes drawn from ordinary valid inputs found **zero**. Ten
probes reaching past what the tests exercise found **nine**. A rule that
only fires on `0-99` cannot be exposed by inputs nobody sends.

Probes must NOT come from the task's own tests. That is the circularity
that made the ruler fit the table: weak tests give weak inputs, agreement
follows by construction, and nothing is ever found.

Two independent sources ray already has and does not yet use here:

- **Boundary values from the mutants themselves.** A constant mutated
  `n -> n+1` is the code stating that `n` is a boundary worth probing.
  `mutate.BoundaryInputs` already derives these.
- **dep-harvest.** Values a pinned dependency's own test suite exercises.

Currently the probes are hand-written. That is the honest gap.

## Grader soundness, per obligation

Layer 2 works **per expanded combination, not per visual row** — one
Markdown row can carry many obligations through `any` or compound cells,
and a gap can hide inside a row that looks covered.

For each combination:

1. expand it from the frozen spec
2. construct a violation targeted at that obligation alone
3. confirm with a witness that the modified solution actually violates it
4. run the declared test and the full verifier
5. the violating solution passes → **proven false positive**

**Isolation is required for the enforcement verdict.** A killed violation
counts as evidence only when the edit is confined to the stated
obligation. If it also breaks unrelated behaviour, the result is
inconclusive, not covered.

Measured instance: deleting the wrap-around guard also emptied the range,
so a *different* rule raised the same exception type and the declared
test `test_wrap_around_range_raises` still passed. Declaration alone
called the row covered; it is a proven false positive.

### Mutation does not answer this

Killing operator and constant mutations does not establish that omitted
requirements, deleted checks, missing calls, wrong algorithms, or
protocol violations are detected. "All generated mutants were killed" is
not "all requirements are enforced" — measured directly: `mutation`
printed *"75 mutant(s), all caught by the tests"* on a task with five
unenforced requirements. It must not gate a verdict.

## Done 2026-08-27

1. **Layer 2, both halves.** Declarative cross-reference plus executable
   verification with the isolation check. On the cron fixture: 7 of 32
   combinations have no declared test, and 5 obligations are **proven**
   false positives — violation applied, confirmed by witness, full
   verifier still green.
2. **Mutation demoted to advisory.** It renders as `i (advisory)` and
   contributes to the verdict in neither direction — it can no longer
   certify, and its absence can no longer block. It was printing "75
   mutant(s), all caught by the tests" beside those five proven false
   positives.
3. **Sufficiency reworded** — report the exact artifact/property
   disagreement, never claim that Markdown itself was "violated" or malformed.

## Universality, as measured

The whole surface is four task-supplied strings — where the source is,
how to read and write it, how to run the verifier, and how to read its
verdict. Nothing in `ray` knows a language, a runner, or a project
layout, because the only operations are "replace text in a file" and
"run a command".

| axis | fixture | result |
|---|---|---|
| Python / pytest, local source | cron | 5 proven false positives |
| Go / `go test`, local source | ray's own `specparser` | 2 proven false positives, in ray itself |
| Source inside a container | cron in `python:3.12-slim` | identical 5 |
| Verdict in a file, not exit status | same, `reward.txt` | identical 5 |
| Verifier that always exits 0 | same | identical 5 |
| Tests not on this filesystem | same, via `test_list` | coverage cross-referenced 32 combinations |

Every fixture's source was restored intact and verified after each run.

Rust and C++ have no fixture run. The mechanism is identical — text
replacement plus a command — so the risk is a config detail, not a
missing capability. Not claimed until run.

## Both obligations, one canonical property model

Both are derived from the same digest-bound formal-property IR, so they cannot
drift apart. The witness authored for an obligation serves both:

- **A (`conform`)** — run the witness on the UNMODIFIED solution; does it
  do what the row requires?
- **B (`enforce`)** — break the row, confirm the change, run the
  verifier; does the declared test reject it?

**Both gate on witness relevance.** If breaking the rule does not change
what the witness observes, the witness is blind to that rule and is
evidence about nothing, in either direction. Found by a real authoring
slip: the non-string-expression witness passed a string, never reached
the rule, and obligation A reported the solution VIOLATED when the
solution was correct and the witness was wrong. Once fixed, the same two
rows became proven false positives under obligation B.

Only a Required-behavior clause in a decidable form (`raise <Type>
containing "<text>"`) is judged automatically. Everything else is
inconclusive and blocks certification. On cron, 21 of 32 requirements
come back undecided — which is the honest number, not a failure.

## What to build next, in order

1. **Drive `oracle` and `diff-test` from canonical property IR** for the
   requirements `conform` cannot decide from a witness alone — the
   unbounded representations where a formal property is needed.
2. **Obligation coverage of the spec.** 9 violations were authored for
   the cron fixture against 32 combinations; the rest correctly come back
   inconclusive, so the spec is not fully discharged and the task cannot
   be certified. That is the intended behaviour, not a defect.
3. **Materialising a patch-shaped task.** The container fixture used
   pre-applied source. A real deep-swe task needs `base_commit` checked
   out and `solution.patch` applied first — the author's setup step, not
   `ray`'s, since `ray` attaches to an environment rather than managing
   one.

## Open questions

- How a row is paired with its test. Textual matching is ruled out by
  measurement. Candidates: author-declared mapping written alongside each
  row, or breaking the requirement and observing the suite. Both are
  authoring work; neither is automatic.
- Whether `spec.md` rows should carry their own violation (the edit that
  breaks exactly that row), making the pairing executable rather than
  declarative.
- `ray.toml` schema — now needs the test command and the pass signal,
  which were not anticipated.
- Whether AI-authored `spec.md` is reliable enough without mandatory
  human review. Still unmeasured.
