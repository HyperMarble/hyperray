# ray v0.1.0 — Design

## What this is

`ray` is a deterministic correctness engine for coding tasks. Given a
task's spec, tests, and solution, it checks whether they actually agree
with each other — not by running the test suite and calling it done, but
by checking the spec itself is complete, generating full combinatorial
coverage of every case the spec defines, proving a simplified reference
model correct against the spec, and differentially testing the real
solution against that proof.

## Why this exists

Test suites passing does not prove a solution is correct — it proves the
solution agrees with whatever specific examples someone thought to write.
A test suite can be complete-feeling and still miss a real requirement
(a stated behavior with zero test covering it), or over-constrain a
correct solution (a test asserting something the spec never actually
required). Both failure modes were hit repeatedly authoring a real Olympus
task this session: a panel-instance-ordering bug untested because every
example happened to use alphabetically-ordered data, a capability-tag
leak untested because no mock forecaster modeled a realistic
non-self-normalizing wrapped forecaster, a columns-matching bug where the
solution's `.identical()` check was stricter than the prompt's own stated
contract.

## Where `ray` sits

`ray` is a **task-verification layer**, not an eval-environment layer.
Frameworks like Harbor and Inspect assume a task is already correct and
grade an *agent's* performance against it. `ray` runs upstream of that:
it checks whether the *task itself* — its spec, tests, and solution — is
internally sound, before any agent, or any eval framework, ever touches
it. A `ray`-verified task is meant to become a valid Harbor/Inspect task
afterward, not a replacement for either.

```
  write task  →  ray check  →  (if sound) load into Harbor/Inspect  →  run agents, grade performance
```

## Scope for v0.1.0

- **Coding tasks only.** No non-code "work" verification (that's a
  separate, later, and substantially different problem, out of scope
  here).
- **Python, Rust, and C++ solution targets.** The oracle-proof layer
  (layer 3) depends on a per-language formal-verification tool
  existing — confirmed available for Python (`deal-solver`/Z3), Rust
  (Verus), and C++ (ESBMC). No equivalent was found for Go. Go targets
  are explicitly deferred, not silently unsupported forever — layers
  1, 2, and 4 are language-agnostic and could run on a Go task today;
  only layer 3 is blocked, pending a suitable tool.
- **CLI-first, library-usable.** `ray check <task-dir>` is the primary
  interface, but the four verifiers are also callable as a library
  (needed for later per-request/inline use cases outside this v0.1.0
  scope, not designed here in detail, but the interface must not
  foreclose it).

## Task bundle format

Mirrors the shape already proven by Harbor, and already the de facto
standard on Shipd and AfterQuery task packages:

```
task/
  instruction.md       # human-readable prose (the "issue")
  spec.md               # the fixed, precise spec — condition table(s)
  ray.toml              # config: verifier timeouts, language target, etc.
  environment/
    Dockerfile
  tests/
    ...
  solution/
    ...
```

`instruction.md` and `spec.md` are deliberately separate artifacts (see
"Spec vs. instruction," below) — `ray` only reads `spec.md`;
`instruction.md` is for humans and downstream eval frameworks.

### Spec vs. instruction

Two different jobs, two different files:

- **`instruction.md`** — the issue. Human-facing, prose, allowed to be
  a little loose because a human reads it for intent. This is what
  becomes the Shipd Task Prompt / Harbor `instruction.md`.
- **`spec.md`** — the precise technical contract. Written as Markdown
  condition tables: parameters, their discrete values, and the required
  behavior for each combination. Unambiguous by construction — a
  well-written spec table cannot be read two different ways the way
  prose can.

`ray` derives everything (completeness check, combinatorial coverage,
oracle model, differential tests) from `spec.md`, never from
`instruction.md` directly.

## The four verifiers

Each verifier implements one shared interface:

```go
type Verifier interface {
    Run(task TaskState) (Result, error)
}

type Result struct {
    Pass        bool
    Explanation string          // which clause/combination/line, and why
    Metadata    map[string]any  // structured detail for machine consumption
}
```

`ray check` runs them in order, stops at the first failure, and reports
which verifier failed and why — not just an aggregate pass/fail.

### 1. `spec-lint`

Custom implementation (no maintained tool exists — the original SCR
toolset this idea comes from has no current distribution). Parses
`spec.md`'s condition tables and checks two properties:

- **Completeness** — every combination of parameter values has exactly
  one defined row. No combination is left with an undefined behavior.
- **Disjointness** — no two rows define conflicting behavior for the
  same combination.

Fails fast, before any of the following three layers run, since they're
only meaningful against a spec that's already internally consistent.

### 2. `coverage`

Wraps **PEV** (NIST, `pev.jar`, real and currently downloadable from
`usnistgov/combinatorial-testing-tools`). Takes `spec.md`'s parameters
and values, generates the minimal test-case table covering every t-way
combination, and cross-references it against the actual test file:
flags any required combination with zero matching test.

### 3. `oracle`

Takes a hand-written simplified reference model — plain, dependency-free
code in the target language (no pandas/library complexity) — and proves
it correct against `spec.md`. The actual prover is per-language, since
no single tool spans all three:

| Target | Prover | Notes |
|---|---|---|
| Python | `deal-solver` (Z3-backed) | Contracts as `@deal.pre`/`@deal.post` decorators |
| Rust | Verus | Contracts as `requires`/`ensures` clauses |
| C++ | ESBMC | Function-contract-based, Z3-backed |

Go is not supported at this layer — no equivalent tool was found.
Layers 1, 2, and 4 remain available for Go tasks; only the oracle proof
is blocked, pending a suitable tool.

This is the one piece of the pipeline that is **not** fully automatable
today, regardless of target language — writing the simplified model is
real, bounded, per-task work. No tool was found (searched specifically)
that automatically abstracts a simplified verifiable model from
complex, library-heavy code such as the kind of solution `ray` targets.

### 4. `diff-test`

Generates property-based test cases (Hypothesis) from `spec.md`, runs
both the real solution and the layer-3-proven oracle on each generated
input, and reports any disagreement. A mismatch is a certain, proven
bug (the oracle side is mathematically correct); agreement across many
generated cases is strong evidence, not literal proof, for the real
implementation (Z3 cannot reason through pandas/library internals
directly — this is the one honest residual gap in the whole pipeline,
and it is a property of the real implementation's environment/library
dependencies, not a flaw in `ray`'s method).

## Distribution

Single static Go binary. Installable via:

- `curl -sSL https://get.<domain>/ray | sh`
- `brew install hypermarble/tap/ray`

Both generated from one `goreleaser` config (the same toolchain used by
`gh`, `git-lfs`, and most Go CLIs distributed this way). `ray` itself
never requires the end user to manage a Python/Rust/C++ toolchain
directly — it shells out to `java -jar pev.jar` for layer 2 always, and
for layer 3 to whichever prover matches the task's target language
(`deal-solver` for Python, `verus` for Rust, `esbmc` for C++), each
managed/bundled per target rather than assumed to be pre-installed.

## Explicitly out of scope for v0.1.0

- **Go solution targets** — no oracle-layer tool exists today. Layers
  1, 2, and 4 could run on Go tasks; layer 3 cannot, until a suitable
  tool is found or built.
- Any language beyond Python/Rust/C++/Go — not evaluated yet.
- Per-request / inline runtime integration (a real, separate future
  direction; the interface is kept clean enough not to block it, but
  it is not designed in detail here).
- PyPI publication (local build + brew/curl only for now).
- Any non-code "work" verification.

## Open questions for implementation planning

- Exact `ray.toml` schema (verifier timeouts, language target flag,
  spec-table parser options).
- Where the bundled/managed Python environment for layers 3/4 actually
  lives (vendored venv vs. requiring `python3` + `pip install` on
  first run).
- Exact Markdown condition-table grammar for `spec.md` (need a strict,
  parseable subset of Markdown tables, not free-form prose-with-tables).
