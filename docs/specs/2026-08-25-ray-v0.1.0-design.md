# ray v0.1.0 — Design

## What this is

`ray` is a deterministic correctness engine for coding tasks. Given a
task's spec, tests, and solution, it checks whether they actually agree
with each other — not by running the test suite and calling it done, but
by checking the spec itself is complete, generating full combinatorial
coverage of every case the spec defines, proving a simplified reference
model correct against the spec, and differentially testing the real
solution against that proof.

## Why this exists

Test suites passing does not prove a solution is correct — it proves the
solution agrees with whatever specific examples someone thought to write.
A test suite can be complete-feeling and still miss a real requirement
(a stated behavior with zero test covering it), or over-constrain a
correct solution (a test asserting something the spec never actually
required). Both failure modes were hit repeatedly authoring a real Olympus
task this session: a panel-instance-ordering bug untested because every
example happened to use alphabetically-ordered data, a capability-tag
leak untested because no mock forecaster modeled a realistic
non-self-normalizing wrapped forecaster, a columns-matching bug where the
solution's `.identical()` check was stricter than the prompt's own stated
contract.

## Where `ray` sits

`ray` is a **task-verification layer**, not an eval-environment layer.
Frameworks like Harbor and Inspect assume a task is already correct and
grade an *agent's* performance against it. `ray` runs upstream of that:
it checks whether the *task itself* — its spec, tests, and solution — is
internally sound, before any agent, or any eval framework, ever touches
it. A `ray`-verified task is meant to become a valid Harbor/Inspect task
afterward, not a replacement for either.

```
  write task  →  ray check  →  (if sound) load into Harbor/Inspect  →  run agents, grade performance
```

### This is a consumer-driven contract, not a novel idea

`spec.md` is `ray`'s version of what large engineering orgs already call
a **consumer-driven contract**: a precise statement of exactly what
behavior *we* depend on from our own code and its dependencies, owned
and tested by us, independent of whatever a dependency's own maintainers
happened to test. Industry's own framing of the problem `ray` solves:
*"Silent gaps create the worst outcome when reviewers approve [a change]
because the tests are green, while nobody realizes the green tests are
unrelated to the behavior that changed."* `ray`'s four (see below, five)
layers are what make that contract rigorous instead of just prose.

## Scope for v0.1.0

- **Coding tasks only.** No non-code "work" verification (that's a
  separate, later, and substantially different problem, out of scope
  here).
- **Python, Rust, and C++ solution targets.** The oracle-proof layer
  (layer 3) depends on a per-language formal-verification tool
  existing — confirmed available for Python (`touchstone-prover`, Z3+cvc5), Rust
  (Verus), and C++ (ESBMC). No equivalent was found for Go. Go targets
  are explicitly deferred, not silently unsupported forever — layers
  1, 2, and 4 are language-agnostic and could run on a Go task today;
  only layer 3 is blocked, pending a suitable tool.
- **CLI-first, library-usable.** `ray check <task-dir>` is the primary
  interface, but the five components are also callable as a library
  (needed for later per-request/inline use cases outside this v0.1.0
  scope, not designed here in detail, but the interface must not
  foreclose it).

## Task bundle format

Mirrors the shape already proven by Harbor, and already the de facto
standard on Shipd and AfterQuery task packages:

```
task/
  instruction.md       # human-readable prose (the "issue")
  spec.md               # the fixed, precise spec — condition table(s)
  ray.toml              # config: verifier timeouts, language target, etc.
  environment/
    Dockerfile
  tests/
    ...
  solution/
    ...
```

`instruction.md` and `spec.md` are deliberately separate artifacts (see
"Spec vs. instruction," below) — `ray` only reads `spec.md`;
`instruction.md` is for humans and downstream eval frameworks.

### Spec vs. instruction

Two different jobs, two different files:

- **`instruction.md`** — the issue. Human-facing, prose, allowed to be
  a little loose because a human reads it for intent. This is what
  becomes the Shipd Task Prompt / Harbor `instruction.md`.
- **`spec.md`** — the precise technical contract. Written as Markdown
  condition tables: parameters, their discrete values, and the required
  behavior for each combination. Unambiguous by construction — a
  well-written spec table cannot be read two different ways the way
  prose can.

`ray` derives everything (completeness check, combinatorial coverage,
oracle model, differential tests) from `spec.md`, never from
`instruction.md` directly.

**Review caution, not a reassurance:** a wrong row in a clean spec table
is *harder* to visually catch than a wrong sentence in loose prose, not
easier — structured/tabular output that's wrong still looks uniformly
plausible, correctly formatted, indistinguishable from a correct row
next to it. Whoever authors `spec.md` (human or AI) needs deliberate,
row-by-row review specifically because the format's tidiness doesn't
make errors more visible; if anything it hides them better than prose
would. This is not a settled-safe step just because it's structured.

## The five components

Each verifier implements one shared interface:

```go
type Verifier interface {
    Run(task TaskState) (Result, error)
}

type Result struct {
    Pass        bool
    Explanation string          // which clause/combination/line, and why
    Metadata    map[string]any  // structured detail for machine consumption
}
```

`ray check` runs them in order, stops at the first failure, and reports
which verifier failed and why — not just an aggregate pass/fail.

### 1. `spec-lint`

Custom implementation (no maintained tool exists — the original SCR
toolset this idea comes from has no current distribution). Parses
`spec.md`'s condition tables and checks two properties:

- **Completeness** — every combination of parameter values has exactly
  one defined row. No combination is left with an undefined behavior.
- **Disjointness** — no two rows define conflicting behavior for the
  same combination.

Fails fast, before any of the following three layers run, since they're
only meaningful against a spec that's already internally consistent.

### 2. `coverage`

Wraps **PEV** (NIST, `pev.jar`, real and currently downloadable from
`usnistgov/combinatorial-testing-tools`). Takes `spec.md`'s parameters
and values, generates the minimal test-case table covering every t-way
combination, and cross-references it against the actual test file:
flags any required combination with zero matching test.

### 3. `oracle`

Takes a hand-written simplified reference model — plain, dependency-free
code in the target language (no pandas/library complexity) — and proves
it correct against `spec.md`. The actual prover is per-language. All
three confirmed as the strongest available option in their language,
not just the first one found (checked directly, not assumed):

| Target | Prover | Notes |
|---|---|---|
| Python | **touchstone-prover** (Z3 + cvc5, cross-validated) | `@require`/`@ensure` string-expression contracts; hands-on confirmed to prove loops, recursion, lists, sets with automatically-inferred loop invariants — dramatically more capable than `deal-solver`, which by its own documentation admits it lacks loop-invariant support and is "more proof-of-concept... [not] part of your day-to-day tooling" |
| Rust | **Verus** | Contracts as `requires`/`ensures` clauses; confirmed state-of-the-art, used on real large systems as of 2026 |
| C++ | **ESBMC** | Function-contract-based, Z3-backed; confirmed dominant via competition results (2nd in ReachSafety, 1st Overall Test-COMP four years running, 2023–2026) |

All three ultimately compile down to the **same underlying Z3 engine**
(touchstone additionally cross-validates with cvc5) — they are different
best-in-class *frontends* translating one language's syntax into Z3's
constraint language, not three independently-limited technologies. The
practical capability difference between tools (e.g. `deal-solver` vs.
`touchstone`, both Z3-backed) lives entirely in how much of the real
language the frontend can translate, not in the underlying prover.

Go is not supported at this layer — no equivalent tool was found. This
is a "nobody has built the frontend yet" gap, not a structural one: Z3
has official Go bindings, and Go's static typing is if anything easier
to translate than Python's dynamic typing. Building a minimal Go
frontend is a real, scoped v0.2.0+ candidate, not blocked research.
Layers 1, 2, and 4 remain available for Go tasks today regardless.

**This is the one piece of the pipeline that is not fully automatable,
regardless of target language or prover strength** — confirmed
structurally, not just as a tooling gap: none of these tools has direct
access to a dynamic/complex library's internals (confirmed hands-on:
`touchstone` returns `UNKNOWN — unmodeled module-qualified call
pd.Index(...)` the moment real pandas is involved, the same shape of
limitation the tool's own demo shows for any unmodeled external call).
Writing the simplified model is real, bounded, per-task work — but
`touchstone`'s expanded language support (loops, recursion, collections)
makes what's *writable inside* that simplified model dramatically less
restrictive than a `deal-solver`-era model would have been.

### 4. `diff-test`

Generates property-based test cases (Hypothesis) from `spec.md`, runs
both the real solution and the layer-3-proven oracle on each generated
input, and reports any disagreement. A mismatch is a certain, proven
bug (the oracle side is mathematically correct); agreement across many
generated cases is strong evidence, not literal proof, for the real
implementation (Z3 cannot reason through pandas/library internals
directly — this is the one honest residual gap in the whole pipeline,
and it is a property of the real implementation's environment/library
dependencies, not a flaw in `ray`'s method).

### 5. `dep-harvest`

Given a task's pinned dependency (e.g. `pandas==2.x`, read from
`environment/`), fetches that exact version's own test suite from its
upstream repo and extracts the cases relevant to the specific functions
the task's solution actually calls — not the whole suite, just the
slice that matters. The fetch-and-extract only happens **once per
`(dependency, exact version)` ever seen**, cached as a content-addressable
artifact (via `ORAS`/an OCI-compatible registry, or a local equivalent)
the same way Docker deduplicates layers by hash — every later task
pinning the same version pulls the cached extract instead of re-cloning
and re-extracting from scratch. Output is shaped as **PEV-ready value lists**, not
raw scenarios: for each spec parameter the harvested cases inform (e.g.
`columns_match`), the real tricky values a dependency's own maintainers
already considered worth testing (a NaN-containing index, a
dtype-mismatched pair, an empty index) get added to that parameter's
value list, so layer 2's combinatorial engine crosses them against every
other spec dimension automatically — producing combinations like
*"NaN-containing columns" × "panel mode: yes" × "contiguous: yes"* that
neither a human nor a hand-picked parameter list would likely construct.

**Honest, checked limit, not assumed:** this surfaces what the
dependency's *own* maintainers thought to test, not literally all
possible behavior — pandas' own measured coverage is 97% (confirmed via
its live Codecov badge, not just its 82% CI gate threshold, which is a
minimum bar, not the real number). A ~3% residual gap remains where
`dep-harvest` provides no signal at all.

**This does not replace layers 1–4, and per real industry practice, it
isn't meant to.** The actual safety net for *unknown* silent
divergence is the consumer-driven contract itself (`spec.md`, tested via
layers 1 and 3, independent of what any dependency's suite covers) —
`dep-harvest` only enriches it with real, free, already-known edge cases
on top. Mislabeling its output as "complete" would recreate the exact
false-confidence failure mode this whole design exists to close.

## Distribution

Single static Go binary. Installable via:

- `curl -sSL https://get.<domain>/ray | sh`
- `brew install hypermarble/tap/ray`

Both generated from one `goreleaser` config (the same toolchain used by
`gh`, `git-lfs`, and most Go CLIs distributed this way). `ray` itself
never requires the end user to manage a Python/Rust/C++ toolchain
directly — it shells out to `java -jar pev.jar` for layer 2 always, and
for layer 3 to whichever prover matches the task's target language
(`touchstone` for Python, `verus` for Rust, `esbmc` for C++), each
managed/bundled per target rather than assumed to be pre-installed.

## Explicitly out of scope for v0.1.0

- **Go solution targets** — no oracle-layer tool exists today. Layers
  1, 2, and 4 could run on Go tasks; layer 3 cannot, until a suitable
  tool is found or built.
- Any language beyond Python/Rust/C++/Go — not evaluated yet.
- Per-request / inline runtime integration (a real, separate future
  direction; the interface is kept clean enough not to block it, but
  it is not designed in detail here).
- PyPI publication (local build + brew/curl only for now).
- Any non-code "work" verification.

## Open questions for implementation planning

- Exact `ray.toml` schema (verifier timeouts, language target flag,
  spec-table parser options).
- Where the bundled/managed Python environment for layers 3/4 actually
  lives (vendored venv vs. requiring `python3` + `pip install` on
  first run).
- Exact Markdown condition-table grammar for `spec.md` (need a strict,
  parseable subset of Markdown tables, not free-form prose-with-tables).
- `dep-harvest`'s exact fetch mechanism: cache the harvested extract as
  a content-addressable artifact keyed by `(dependency, exact version)`
  — via `ORAS`/an OCI-compatible registry, or a local equivalent — so
  the clone-and-extract work happens once per pinned version ever seen,
  not once per task run, mirroring how Docker/OCI already deduplicate
  layers by content hash.
- Mapping a solution's actual function calls to the relevant slice of a
  dependency's test suite, and mapping harvested values to the `spec.md`
  parameter each belongs to: AI-performed given a precise spec (this is
  a semantic-matching task, not one requiring a human specifically), but
  inherits the same review caution as spec-writing itself — a wrong
  mapping is a structured-output error, not visually distinct from a
  correct one, and needs the same deliberate review, not a free pass
  just because the matching step itself is easy for a model.
- Whether AI-authored `spec.md` reliability (as opposed to prose or
  open-ended formal-logic spec authoring, which research shows is
  genuinely hard, ~57.8% even for frontier models) needs a dedicated
  benchmark before being trusted without mandatory human review — not
  measured either way tonight, deliberately left open rather than
  assumed in either direction.
